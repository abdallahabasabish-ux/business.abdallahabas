# إجراء النسخ الاحتياطي والاستعادة — نظام CRM

**المشروع:** crm-system-2ee41
**التاريخ:** 3 نوفمبر 2026
**الأولوية:** إلزامية قبل أي تعديل على قاعدة البيانات أو قواعد الأمان

---

## 1. قبل البدء — إعداد Cloud Storage للنسخ الاحتياطي

قبل أول نسخة احتياطية، يجب إنشاء حاوية Cloud Storage مخصصة للنسخ:

1. افتح [Google Cloud Console](https://console.cloud.google.com/).
2. اختر مشروع: `crm-system-2ee41`.
3. اذهب إلى **Storage → Browser → Create Bucket**.
4. اسم الحاوية: `crm-system-2ee41-backups`.
5. المنطقة: نفس منطقة Firestore (غالبًا `us-central1`).
6. فئة التخزين: `Standard` (للوصول السريع).
7. اضبط **Lifecycle**: حذف النسخ الأقدم من 90 يومًا تلقائيًا (لتوفير المساحة).

---

## 2. إنشاء نسخة احتياطية يدوية (قبل كل تعديل جوهري)

### الطريقة الأولى: من وحدة تحكم Firebase (الأسهل)

1. افتح [Firebase Console](https://console.firebase.google.com/) → مشروع `crm-system-2ee41`.
2. اذهب إلى **Firestore Database → التبويب «Data»**.
3. اضغط **⋯ (القائمة)** أعلى يمين → **Export**.
4. اختر الحاوية: `crm-system-2ee41-backups`.
5. اختر **All collections** (لتصدير كل المجموعات).
6. اضغط **Export**.
7. انتظر اكتمال التصدير (قد يستغرق 5-30 دقيقة حسب حجم البيانات).
8. تحقق من اكتمال التصدير في Cloud Storage Browser.

### الطريقة الثانية: عبر Firebase CLI (للمستخدمين المتقدمين)

```bash
# تثبيت Firebase CLI (إن لم يكن مثبتًا)
npm install -g firebase-tools

# تسجيل الدخول
firebase login

# تعيين المشروع
firebase use crm-system-2ee41

# تصدير كل البيانات
gcloud firestore export gs://crm-system-2ee41-backups/backup-$(date +%Y%m%d-%H%M%S)
```

## 4. التحقق من قابلية الاستعادة (إلزامي قبل التعديلات الحرجة)

قبل الاعتماد على نسخة احتياطية، اختبر استعادتها على مشروع اختبار:

### إنشاء مشروع اختبار (مرة واحدة)

1. أنشئ مشروع Firebase جديد باسم `crm-system-test`.
2. فعّل Firestore في وضع الإنتاج.
3. اضبط نفس تكوين المشروع الأساسي.

### اختبار الاستعادة

```bash
# استعادة في مشروع الاختبار
gcloud config set project crm-system-test
gcloud firestore import gs://crm-system-2ee41-backups/backup-YYYYMMDD-HHMMSS

# تحقق من البيانات عبر وحدة التحكم
# - عدد المستندات في كل مجموعة
# - عينة من السجلات
# - العلاقات بين البيانات
```

إذا نجحت الاستعادة على مشروع الاختبار، فالنسخة موثوقة.

## 5. إجراء الاستعادة على الإنتاج (في حالات الطوارئ فقط)

⚠️ **تحذير:** الاستعادة على الإنتاج تستبدل البيانات الحالية. استخدمها فقط في حالات:
- فقدان بيانات جسيم
- تلف في السجلات بسبب تعديل خاطئ
- هجوم أدى لتدمير البيانات

### خطوات الاستعادة

```bash
# 1. إنشاء نسخة احتياطية للوضع الحالي (حتى لو كان تالفًا)
gcloud config set project crm-system-2ee41
gcloud firestore export gs://crm-system-2ee41-backups/emergency-backup-$(date +%Y%m%d-%H%M%S)

# 2. الاستعادة من النسخة المعروفة الجيدة
gcloud firestore import gs://crm-system-2ee41-backups/backup-YYYYMMDD-HHMMSS

# 3. التحقق من البيانات عبر وحدة التحكم
# 4. إشعار جميع المستخدمين بإعادة التشغيل
```

## 6. استعادة الشيفرة البرمجية (Code Rollback)

إذا احتاجت الترقية إلى تراجع برمجي:

### عبر Git (موصى به قبل أي ترقية)

```bash
# قبل بدء الترقية، أنشئ وسمًا
git tag pre-upgrade-phase2
git push origin pre-upgrade-phase2

# للتراجع
git checkout pre-upgrade-phase2
# أو
git revert <commit-hash>
```

### عبر نسخ الملفات (بدون Git)

```bash
# قبل الترقية
cp -r CRM-System-main CRM-System-main-backup-$(date +%Y%m%d)

# للتراجع
cp -r CRM-System-main-backup-YYYYMMDD/* CRM-System-main/
```

## 7. استعادة قواعد الأمان (Rules Rollback)

### الاحتفاظ بنسخة من القواعد القديمة

قبل نشر قواعد أمان جديدة:

```bash
# تصدير القواعد الحالية (من وحدة التحكم أو CLI)
firebase firestore:rules:get > firestore.rules.old

# أو احتفظ بنسخة من كل إصدار
cp firestore.rules firestore.rules.v1-$(date +%Y%m%d)
```

### للتراجع عن القواعد

```bash
# استبدال القواعد بالنسخة القديمة
cp firestore.rules.old firestore.rules

# نشر القواعد القديمة
firebase deploy --only firestore:rules
```

## 8. جدول النسخ الاحتياطي الدوري

| التكرار | المجموعات | السبب |
|---------|-----------|-------|
| قبل كل تعديل جوهري | الكل | قاعدة إلزامية |
| يوميًا (تلقائي) | payments, treasury, orders | البيانات المالية الحرجة |
| أسبوعيًا (تلقائي) | الكل | نسخة كاملة دورية |
| قبل كل نشر جديد | الكل | قاعدة إلزامية |

### إعداد النسخ اليومي التلقائي (عبر Cloud Scheduler — مجاني)

```bash
# إنشاء وظيفة مجدولة لتصدير يومي
gcloud firestore export gs://crm-system-2ee41-backups/daily-$(date +%Y%m%d) \
  --async
```

ملاحظة: Cloud Scheduler على Firebase Spark Plan محدود. يمكن جدولة التصدير عبر:
- Cron job على جهاز محلي
- GitHub Actions (مجاني للمشاريع العامة)
- خدمات جدولة خارجية مجانية

## 9. قائمة التحقق قبل أي تعديل جوهري

استخدم هذه القائمة قبل نشر أي تغيير على الإنتاج:

- [ ] تم إنشاء نسخة احتياطية كاملة اليوم
- [ ] تم التحقق من قابلية الاستعادة على مشروع اختبار
- [ ] تم توثيق مسار النسخة الاحتياطية في `backup-log.md`
- [ ] تم إنشاء وسم Git `pre-<phase>` قبل التغييرات
- [ ] تم الاحتفاظ بنسخة من قواعد الأمان الحالية
- [ ] تم اختبار التغييرات على بيئة محلية (Firebase Emulator)
- [ ] تم إعداد خطة تراجع موثقة
- [ ] تم إبلاغ المستخدمين بوقت التوقف المتوقع (إن وُجد)

## 10. نقاط عدم التراجع (لا يمكن استعادتها)

توخَّ الحذر: هذه الإجراءات **لا يمكن التراجع عنها**:

- حذف مشروع Firebase بالكامل
- حذف مستخدم من Firebase Auth (لا يمكن استعادة الحساب)
- حذف مجموعة Firestore بأكملها من وحدة التحكم (النسخة الاحتياطية فقط تُنقذ)
- تغيير معرّف مشروع Firebase

**القاعدة الذهبية:** إذا لم تكن متأكدًا، لا تفعله. اسأل أولًا.
